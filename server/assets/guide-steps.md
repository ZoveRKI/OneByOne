`steps` 里每一项的字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | 是 | 步骤标题，一句话说清这一步做了什么 |
| `hunks` | 否 | 引用的改动块 id（上面每个 `###` 标题开头的编号），可以跨多个文件；概览步骤留空 |
| `explain` | 否 | 讲解，支持简单 Markdown：段落、列表、`行内代码`、**加粗** |
| `id` | 否 | 步骤 id，给 `related` 引用 |
| `chapter` | 否 | 章节名，同一章节的步骤要放在一起 |
| `kind` | 否 | `add` 新增、`modify` 修改、`delete` 删除、`refactor` 重构、`fix` 修复、`test` 测试、`config` 配置、`docs` 文档、`style` 样式 |
| `related` | 否 | 关联步骤的 id 列表 |

### 要求

1. **覆盖全部改动块**：清单里的每个 id 至少出现在一个步骤里。和主题无关的顺手修改也要单独列出来并如实说明（例如"顺手把分页大小从 20 改成 50"），不要隐瞒，也不要混进不相关的步骤。
2. **按理解顺序排列，不按修改顺序**：一般自底向上——数据结构和类型 → 工具函数 → 核心逻辑 → 接口 → 界面 → 测试 → 配置和文档。被依赖的部分先讲。
3. **一步讲一件事**：同一件事分散在多个文件里，就放在同一步（例如重命名一个函数）。一个改动块里混了两件事时，可以在两个步骤里都引用它，分别讲。
4. **第一步写概览**：`hunks` 留空，说明这次改动的目标、整体思路和阅读顺序。
5. **讲解写"为什么"**：每步 2～5 句，说明为什么这样改、有什么取舍、读代码时要注意什么（边界情况、兼容性、潜在风险）。不要逐行复述代码，提到函数名、变量名时用反引号。
6. **改动多时用章节分组**：按层次或功能分成几个章节，章节名要短。
7. 讲解使用中文，除非用户另有要求。
